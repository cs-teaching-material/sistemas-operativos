Bloque conceptual A · Estructura de identidades en Linux

El SO trabaja con números, no con nombres

Cada proceso y archivo en el sistema está asociado a un UID (User ID) y un GID (Group ID) numérico. El nombre de usuario es solo un alias legible para humanos.

# Anatomía de /etc/passwd # usuario:x:UID:GID:comentario:home:shell root:x:0:0:root:/root:/bin/bash daemon:x:1:1:daemon:/usr/sbin:/usr/sbin/nologin www-data:x:33:33::/var/www:/usr/sbin/nologin juan:x:1001:1001:Juan Estudiante:/home/juan:/bin/bash # La 'x' en campo 2 significa que el hash # de contraseña está en /etc/shadow

Rangos convencionales de UID

RangoTipo
0root — superusuario
1 – 99Cuentas de sistema reservadas
100 – 999Usuarios de servicio (sin login)
1000+Usuarios humanos interactivos

/etc/shadow: almacena hashes de contraseñas y política de expiración. Solo accesible por root. Separar hashes de /etc/passwd evita que usuarios sin privilegios lean y ataquen los hashes.

Bloque conceptual A · Anatomía de /etc/shadow y hashes de contraseñas

Cómo Linux almacena y protege las contraseñas

En S23 aprendimos a usar chage y passwd -l. Hoy analizamos por qué funcionan: la estructura interna de /etc/shadow y lo que cada campo significa para el administrador.

# Formato de /etc/shadow: # usuario:hash:ult_cambio:min:max:aviso:inact:expira ana:$6$rounds=5000$salt$hash...:19844:0:90:14:30:: # El prefijo del hash indica el algoritmo: # $1$ → MD5 (inseguro, obsoleto) # $5$ → SHA-256 # $6$ → SHA-512 (estándar actual) # $y$ → yescrypt (Ubuntu 22.04+) # Ver la entrada de shadow de un usuario $ sudo getent shadow ana # Verificar qué algoritmo usa el sistema $ sudo grep "^ENCRYPT_METHOD" /etc/login.defs ENCRYPT_METHOD SHA512

Lectura forense de un campo shadow

El tercer campo (último cambio) es un número entero: días transcurridos desde el 1 de enero de 1970 (epoch Unix). Valor 0 significa que el usuario debe cambiar su contraseña en el próximo inicio de sesión.

# Convertir días epoch a fecha legible $ python3 -c " import datetime dias = 19844 print(datetime.date.fromordinal( datetime.date(1970,1,1).toordinal() + dias ))" 2054-04-19

Un hash comenzando con ! o * en el campo de contraseña indica cuenta bloqueada o sin contraseña habilitada. Las cuentas de servicio deben tener siempre ! o * en este campo.

Bloque conceptual B · nsswitch.conf: cómo el SO busca usuarios

El mecanismo de resolución de nombres de usuario

Cuando un proceso llama a getpwnam("ana"), el kernel no consulta /etc/passwd directamente. Consulta el Name Service Switch (nsswitch), que define el orden y las fuentes de búsqueda.

# /etc/nsswitch.conf # passwd: fuentes para usuarios passwd: files systemd sss ldap # group: fuentes para grupos group: files systemd sss ldap # shadow: fuentes para contraseñas shadow: files sss # El orden importa: primero busca en # 'files' (/etc/passwd), luego systemd, # luego sss (SSSD → LDAP/AD), etc. # Herramienta de diagnóstico getent: $ getent passwd ana # busca en todas las fuentes $ getent group desarrollo $ getent hosts servidor.local

SSSD: conectar Linux a Active Directory

SSSD (System Security Services Daemon): servicio que actúa como proxy entre el sistema y directorios remotos (LDAP, Active Directory, Kerberos).

# Unir servidor Ubuntu a dominio AD $ sudo apt install sssd realmd $ sudo realm join empresa.local \ -U administrador # Ahora 'getent passwd' muestra # usuarios del dominio AD

Con SSSD activo, el inicio de sesión funciona con credenciales de Active Directory sin cuentas locales adicionales.

Bloque conceptual C · sudo y el archivo sudoers

Delegar privilegios sin compartir la contraseña de root

sudo (Superuser Do) permite ejecutar comandos con los privilegios de otro usuario (normalmente root) sin conocer su contraseña. Toda acción con sudo queda registrada en los logs del sistema.

# Editar sudoers de forma segura $ sudo visudo # Formato: usuario HOST=(como_usuario) comandos # Acceso total (el grupo sudo por defecto) %sudo ALL=(ALL:ALL) ALL # Solo reiniciar nginx, sin contraseña deploy ALL=(root) NOPASSWD: /usr/bin/systemctl restart nginx # Solo ver logs de sistema soporte ALL=(root) /usr/bin/journalctl, /usr/bin/tail # Ver permisos del usuario actual $ sudo -l User ana may run: (root) NOPASSWD: /usr/bin/systemctl restart nginx

Principios clave de sudoers

  • Mínimo privilegio: listar solo los comandos necesarios, no ALL sin justificación.
  • NOPASSWD con cuidado: útil en automatización CI/CD, pero elimina la fricción intencional de seguridad.
  • Nunca dar sudo a editores de texto: sudo vim permite escalar a shell root con :!bash.
  • Usar visudo: valida la sintaxis antes de guardar — un sudoers roto puede dejar el sistema sin administración.

Práctica en clase 1 · Gestión de usuarios y sudo granular

Configurar un entorno multiusuario controlado

Escenario: eres el administrador de un servidor de desarrollo. Debes crear cuentas para tres roles distintos con distintos niveles de acceso.

Tareas:

  1. Crear grupo devs y usuario carlos en ese grupo con home y bash.
  2. Crear usuario de servicio appserver sin shell de login ni home.
  3. Crear directorio /var/app con propietario appserver y grupo devs, permisos rwxrwx---.
  4. Configurar con visudo que carlos pueda reiniciar el servicio appserver.service sin contraseña, pero nada más.
  5. Verificar con sudo -l -U carlos que los permisos son correctos.

Verificaciones esperadas:

  • su - appserver debe responder "This account is not available."
  • ls -la /var/app debe mostrar rwxrwx--- y el propietario correcto.
  • sudo -l -U carlos debe mostrar solo el comando permitido.
  • Intentar sudo bash como carlos debe ser denegado.

Bloque conceptual D · PAM: Módulos de Autenticación Conectables

PAM: la capa de autenticación unificada

PAM (Pluggable Authentication Modules): framework de Linux que abstrae la autenticación de las aplicaciones. Un programa como login, sshd o sudo no implementa su propia autenticación — delega a PAM.

PAM permite configurar:

  • Políticas de contraseñas (longitud mínima, complejidad, historial).
  • Límites de intentos fallidos con bloqueo temporal.
  • Autenticación multifactor (TOTP/Google Authenticator).
  • Restricciones de horario de inicio de sesión.
# /etc/security/pwquality.conf # Política de contraseñas minlen = 12 dcredit = -1 # mínimo 1 dígito ucredit = -1 # mínimo 1 mayúscula ocredit = -1 # mínimo 1 especial maxrepeat = 3 # no más de 3 repeticiones # /etc/security/faillock.conf # Bloquear tras 5 intentos fallidos deny = 5 unlock_time = 900 # 15 minutos # Ver cuentas bloqueadas $ sudo faillock --user ana

Bloque conceptual E · Active Directory: gestión centralizada

Active Directory: directorio de identidades empresariales

Active Directory (AD): servicio de directorio de Microsoft que centraliza la autenticación y autorización en redes Windows corporativas. Basado en LDAP y Kerberos.

  • Dominio: conjunto de objetos (usuarios, equipos, grupos) bajo una política unificada.
  • GPO (Group Policy Object): configuraciones que se aplican automáticamente a equipos y usuarios al unirse al dominio.
  • Single Sign-On (SSO): el usuario se autentica una vez y accede a múltiples recursos del dominio.
  • OU (Organizational Unit): contenedor para organizar objetos del dominio y aplicar GPOs diferenciadas.

Bloque conceptual F · DAC vs MAC

Más allá de los permisos POSIX: Control de Acceso Obligatorio

DAC — Discrecional (Linux por defecto)

El dueño del recurso decide quién accede. El dueño puede dar permisos a quien quiera, incluyendo a todos los usuarios del sistema.

Limitación: un usuario comprometido puede cambiar los permisos de sus propios archivos y compartir información sensible. El kernel no limita las decisiones del dueño.

MAC — Obligatorio (SELinux / AppArmor)

La política del sistema define el acceso. Ni el dueño del recurso ni el usuario root pueden saltarse las reglas de la política MAC sin modificarla explícitamente.

Ventaja: incluso si un proceso root es comprometido, MAC puede limitar a qué archivos, puertos y llamadas de sistema tiene acceso.

Herramientas: SELinux (Red Hat/CentOS), AppArmor (Ubuntu/Debian), ya vistos en S23.

En la práctica: Linux usa DAC como capa base (siempre activo) y MAC como capa adicional obligatoria (SELinux/AppArmor). Un proceso debe pasar ambas para acceder a un recurso.

Detectar cuentas problemáticas

Escenario: debes auditar el sistema para identificar posibles riesgos en la configuración de cuentas de usuario.

# 1. Usuarios con UID 0 (equivalentes a root) $ awk -F: '($3 == 0) {print}' /etc/passwd # 2. Cuentas con contraseña vacía $ sudo awk -F: '($2 == "") {print $1}' /etc/shadow # 3.   • Más de un usuario con UID 0.
  • Cuentas de servicio con shell de bash.
  • Usuarios en grupo sudo sin justificación documentada.
  • Logins desde IPs o usuarios no reconocidos.
  • Cuentas de ex-empleados aún activas.

Bloque conceptual G · SID: el UID de Windows

Cómo Windows identifica usuarios internamente

En Windows el identificador único de un usuario o grupo es el SID (Security Identifier), una cadena jerárquica que el kernel usa en cada decisión de acceso — exactamente como Linux usa el UID numérico.

# Ver el SID del usuario actual PS> whoami /user EQUIPO\ana S-1-5-21-3847284093-1842372847-2938471923-1001 # Ver SIDs de todos los grupos del usuario PS> whoami /groups # Estructura de un SID: # S-1-5-21-[dominio]-[RID] # S = Security Identifier # 1 = revisión # 5 = autoridad NT # 21-... = identificador del dominio/máquina # 1001 = RID — identificador relativo del usuario # SIDs predefinidos (equivalen a UIDs fijos en Linux) # S-1-5-18 → SYSTEM (≈ root UID 0) # S-1-5-19 → LOCAL SERVICE # S-1-5-20 → NETWORK SERVICE # S-1-5-32-544 → grupo Administradores

RID: el número que importa

El RID (Relative Identifier) al final del SID es el equivalente funcional del UID en Linux. Por convención:

RIDCuentaEquivalente Linux
500Administrador built-inroot (UID 0)
501Invitado (Guest)nobody
1000+Usuarios creadosUID 1000+

¿Por qué el SID no cambia al renombrar una cuenta? El nombre de usuario es solo un alias. Los permisos de archivos y los ACLs están vinculados al SID, no al nombre. Renombrar "Administrador" a "admin_backup" no cambia sus permisos ni su SID.

El equivalente de PAM y faillock en Windows

Windows gestiona las políticas de contraseñas y bloqueo de cuentas mediante la Directiva de Seguridad Local (secpol.msc) o por GPO en dominios. El equivalente funcional de PAM/pwquality/faillock en Linux.

Directiva de seguridad · Windows · Sesión 2518 / 24
Bloque conceptual G · Cuentas de servicio en Windows

El equivalente de usuarios de servicio sin login

En Linux creamos usuarios de servicio con --shell /usr/sbin/nologin. Windows tiene un sistema análogo con cuentas especiales de servicio que no pueden iniciar sesión interactivamente.

  • Local System (SYSTEM): privilegios máximos en la máquina local. Nunca usar para servicios de aplicación — es el equivalente de correr como root.
  • Network Service: privilegios reducidos, puede autenticarse en red con la identidad del equipo. Equivale a un usuario de servicio con permisos de red.
  • Local Service: privilegios mínimos, sin acceso a red. El más restrictivo — equivalente directo de un usuario nologin en Linux.
  • gMSA (Group Managed Service Account): cuenta de servicio con contraseña rotada automáticamente por AD. La forma moderna y correcta para servicios en dominio.
# Crear cuenta de servicio con mínimos privilegios PS> New-LocalUser "svc_webapp" ` -Password ([System.Security.SecureString]::new()) ` -PasswordNeverExpires $true ` -UserMayNotChangePassword $true ` -Description "Cuenta de servicio webapp - sin login interactivo" # Denegar inicio de sesión interactivo (≈ nologin) # En secpol.msc → Directivas locales → # Asignación de derechos de usuario → # "Denegar el inicio de sesión localmente" # Añadir: svc_webapp # Ver bajo qué cuenta corre un servicio PS> Get-WmiObject Win32_Service | Where-Object {$_.Name -eq "nginx"} | Select-Object Name, StartName Name StartName nginx NT AUTHORITY\LOCAL SERVICE # Cambiar cuenta de un servicio PS> sc.exe config nginx obj= "NT AUTHORITY\LOCAL SERVICE"

Integración curricular · La cadena de control de acceso completa

Cómo se ensamblan los conceptos de Unidad 3

S18 — Permisos POSIX: chmod y chown definen quién puede leer/escribir/ejecutar. Los permisos son la capa de control a nivel de sistema de archivos.

S22 — Amenazas: los atacantes buscan cuentas con contraseñas débiles, servicios corriendo como root y usuarios con sudo sin restricciones para escalar privilegios.

S23 — Hardening: deshabilitar cuentas inactivas, PermitRootLogin no, AppArmor para confinamiento. Las herramientas de S25 son la sustancia de ese hardening.

S24 — Criptografía: las llaves SSH necesitan cuentas correctamente configuradas. La gestión de usuarios es el prerrequisito para que SSH funcione de forma segura.

S25 — Gestión de usuarios: cierra el ciclo. Sin una estructura de identidades correcta (usuarios de servicio, sudo granular, PAM, políticas de contraseñas), todas las demás medidas de seguridad son incompletas.

Herramienta práctica · Checklist de gestión de usuarios segura

Lista de verificación para un servidor en producción

Cuentas:

  • Solo un usuario con UID 0 (root).
  • Cuentas de servicio con nologin o false como shell.
  • Ninguna cuenta con contraseña vacía o por defecto.
  • Cuentas de ex-empleados desactivadas o eliminadas.
  • Política de expiración de contraseñas configurada con chage.

Grupos:

  • Solo usuarios justificados en grupo sudo o wheel.
  • Servicios web no están en grupo docker.
  • Directorios de datos con propietarios de grupo correctos.

sudo:

  • No existen entradas ALL=(ALL) NOPASSWD: ALL sin justificación.
  • Comandos permitidos están en rutas absolutas.
  • No se permite sudo a editores de texto generales.

PAM y políticas:

  • Longitud mínima de contraseña ≥ 12 caracteres.
  • Bloqueo tras 5 intentos fallidos (faillock).
  • Autenticación SSH por llave pública, contraseña deshabilitada.

Este checklist es parte del hardening del servidor y complementa el de S23.

Cuestionario de comprensión

Preguntas de cierre técnico

  1. Un desarrollador te pide acceso root completo al servidor de producción porque "es más cómodo". ¿Qué le propones como alternativa técnica y qué riesgos le explicas?
  2. ¿Por qué ejecutar un servidor web (nginx, apache) como root es un error de seguridad, incluso si el servidor tiene firewall y permisos de archivos correctos?
  3. Explica la diferencia entre bloquear una cuenta con usermod -L y eliminarla con userdel. ¿Cuándo usarías cada opción?
  4. ¿Por qué sudo vim con acceso NOPASSWD puede ser tan peligroso como dar acceso root directo?

Para el proyecto integrador:

La gestión de identidades es transversal a todo el proyecto: los contenedores que desplieguen deben correr con usuarios de servicio sin privilegios, los directorios de datos deben tener propietarios correctos y las llaves SSH deben estar asociadas a cuentas bien definidas. Un sistema sin una estructura de identidades correcta no puede considerarse seguro.
