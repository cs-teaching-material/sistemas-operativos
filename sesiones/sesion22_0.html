Sesión 22:
Taxonomía de Amenazas y Escape del Contenedor

Vulnerando el aislamiento desde Ring 3 hasta Ring 0

Objetivos de la Sesión

  • Definir la taxonomía moderna de amenazas orientada al Kernel y demonios de sistema.
  • Entender los Anillos de Privilegios (Rings) de procesadores x86.
  • Identificar la anatomía de un "Container Breakout" (Escape del contenedor).
  • Comprender los riesgos críticos del montaje de sockets y permisos SUID.
  • Ejecutar prácticas controladas de escalamiento de privilegios local.

Recapitulación S21: La Jaula Dorada

En la S21 vimos cómo los contenedores aíslan procesos usando Namespaces y los limitan usando Cgroups.

A diferencia de las VMs (que tienen un Hypervisor intermedio), los contenedores hablan DIRECTO con el Kernel del Host real.

El Peligro Latente

Si un contenedor es burlado y obtiene acceso directo nivel-Kernel, no hay intermediarios que protejan al servidor físico.

Superficie de Ataque (Attack Surface)

No se ataca un sistema "por arte de magia". Se mapea su superficie de ataque:

  • Vectores de Red: Puertos expuestos al exterior (22 SSH, 80 HTTP).
  • Bibliotecas desfasadas: Código con vulnerabilidades conocidas ejecutándose en memoria.
  • Mala Configuración: Permisos excesivos otorgados a usuarios por error del administrador (Configuración por Defecto).
  • El Motor de Virtualización: El dockerd o el kubelet. Si el orquestador es vulnerable, todos sus hijos caen.

Anillos de Privilegio x86 (Privilege Rings)

Entendiendo el Kernel Space (Ring 0)

El código que se ejecuta en Ring 0 (Kernel Linux / NT) tiene control absoluto sobre el voltaje de la placa madre, los discos, la RAM física y la red.

Los procesos de usuario (tu navegador, tu script de Python, tu contenedor Docker) viven en Ring 3. Tienen estrictamente prohibido tocar el hardware directamente.

Todo ataque moderno busca saltar de Ring 3 a Ring 0 (Privilege Escalation).

Taxonomía de Amenazas Subyacentes

  • Rootkits: Malware inyectado en Ring 0. Puede mentirle al comando ps y a los antivirus porque se ejecuta *debajo* de ellos.
  • Buffer Overflows: Exceder deliberadamente una variable en RAM para reescribir la memoria adyacente y forzar la ejecución de código binario (Shellcode).
  • Zero-Day (0-Day): Vulnerabilidad de la cual el fabricante del software aún no tiene conocimiento. No existe parche o solución al momento del ataque.

Los CVE (Common Vulnerabilities and Exposures)

Diccionario global de vulnerabilidades mantenido por MITRE.

¿Encontraste una forma de crashear el Kernel Linux inyectando un paquete malformado? Lo reportas y se te asigna un código, por ejemplo: CVE-2022-0492 (Cgroups Breakout).

Los administradores cruzan la lista semanal de CVEs contra los sistemas de su empresa para emparchar (Actualizar / Hardening) antes de que un atacante lance un script automatizado.

Escalamiento de Privilegios (PrivSec) Local vs Remoto

Remoto (RCE)

El atacante envía un comando desde internet sin tener usuario en la máquina (Ej. Rompiendo una web en PHP y forzando ejecución desde la IP web).

Local (LPE)

El atacante ya entró al sistema base o al contenedor (quizás era un empleado o vulneró primero la web). Ahora es un usuario común `id=1000 (www-data)`. Su objetivo es convertirse en `id=0 (root)`.

El concepto crítico de permisos SUID

En Linux (El anfitrión típico de Docker), existe un bit especial llamado Set Owner User ID up on execution (SUID).

Si un binario (ej. el comando passwd) tiene el bit SUID activado, significa que cuando un usuario común lo ejecute, el programa funcionará temporalmente con los permisos del creador del archivo (generalmente Root).

Mala configuración = Dejar binarios SUID indebidos, permitiendo que un proceso de usuario adquiera ring level 0 temporalmente y ejecute código malicioso.

Práctica 1: Reconocimiento Manual de SUID

Supongamos que acabamos de comprometer un servidor o contenedor y hemos ganado acceso limitado. El primer paso lógico es buscar archivos que podamos usar en nuestra contra (que tengan SUID root).

# Buscando desde la raíz, ignora errores: $ find / -perm -u=s -type f 2>/dev/null
  • Este comando recorre todo el disco duro viendo si el administrador configuró mal algún ejecutable otorgándole privilegios SUID permanentes.

Escape del Contenedor (Container Breakout)

Imagina que atacas el servidor de la universidad y ganas la shell. Haces un `ls` pero notas que no hay directorios humanos, y el número de procesos es extremadamente bajo.

Descubres con horror que no hackeaste el servidor... hackeaste solo un contenedor Docker de honeypot.

Breakout

Es la serie de técnicas para fracturar los namespaces (S21), salir del entorno aislado y ganar control total del Servidor (El Anfitrión real).

Vector Clásico: Docker Socket Montado

Los desarrolladores son vagos. A veces necesitan que un contenedor invoque a otros contenedores dentro de la infraestructura (Ej. Jenkins CI/CD). Para evitar problemas configuran esto al crear el contenedor:

docker run -v /var/run/docker.sock:/var/run/docker.sock jenkins

El Error Técnico: Le están dando al contenedor interno la llave directa del demonio dockerd padre del sistema anfitrión.

Anatomía del Escape Socket (Paso 1)

Si logro comprometer el contenedor "Jenkins" vulnerable por la web externa y detecto montado el docker.sock, puedo usar el socket para dar órdenes directas al servidor host físico que administra mi encierro.

# Desde adentro de la jaula, ordeno al Host (vía socket): $ docker -H unix:///var/run/docker.sock ps

El contenedor ahora está comandando al demonio que lo enjauló. Es como si el preso le dictara órdenes al director de la prisión.

Anatomía del Escape Socket (Paso 2)

Finalmente, para cristalizar la salida al entorno anfitrión y romper el contenedor, emito la orden final:

$ docker -H unix:///var/run/docker.sock run -it \ -v /:/host debian chroot /host /bin/bash
  • Le pedimos al docker raíz crear OTRO contenedor.
  • Le decimos que monte la raíz TOTA / del servidor físico real dentro de una carpeta /host.
  • Hacemos chroot ahí, escapando completamente a Ring 0 anfitrión.

Práctica 2: El comando prohibido (--privileged)

Hay un flag terrible en docker. A los estudiantes o desarrolladores les da un error de permisos en su contenedor y buscando en internet usan el flag --privileged.

¿Qué hace esto? Apaga drásticamente Cgroups, SecComp y los perfiles de seguridad, permitiéndole al contenedor inyectar memoria directamente en el Kernel de Host.

Práctica 2: Ejecutando el contenedor Inseguro

# Desde tu máquina Host en un ambiente controlado: $ docker run -d --name caja_roto --privileged ubuntu sleep 9000 # Entramos al contenedor supuestamente aislado como simple root interno: $ docker exec -it caja_roto bash

Estamos "aislados". Procedamos a quebrar la pared...

Práctica 2: Generando el Escape en Vivo

El objetivo es leer un archivo del administrador real en el servidor base que el contenedor (por S21 Namespaces) NO debería poder ver.

# Aún dentro de "caja_roto": # 1. Chequeamos a qué disco base tenemos acceso real usando fdisk $ fdisk -l | grep dev # 2. Creamos un punto temporal y montamos a la fuerza el disco real (Host) $ mkdir /escape $ mount /dev/sda1 /escape <-- Esto ESTÁ prohibido en un contendor normal. # 3. Listamos carpetas reales del host: $ ls -la /escape/home/

Conclusiones sobre el Privileged Mode

Pudimos montar el disco /dev/sda1 porque Docker descartó los perfiles de seguridad base y extendió sus "Linux Capabilities" a cap_sys_admin (Omnipotencia total).

REGLA DE INFRAESTRUCTURA: Si estás administrando servidores, una auditoría seria te despedirá (y con razón) si usas contenedores con flag --privileged para servicios de producción no orquestales.

El Kernel Shared (Vulnerabilidades 0-Day)

A pesar de no montar el Docker Socket o usar --privileged, recuerda un riesgo inherente:

El contenedor no es otra máquina. Es tu mismo Kernel. Si el Host está usando Linux Kernel 4.15 y ese kernel es vulnerable a un desbordamiento de caché (Ej. Dirty COW), el proceso contenedor puede ejecutar un exploit que desborde el Kernel maestro e instale un Rootkit. El aislamiento queda obsoleto al instante.

Automatizando la Auditoría: LinPEAS

Los analistas y hackers éticos no ejecutan `find SUID` manualmente todo el día. Utilizan scripts orquestados de reconocimiento:

  • LinPEAS (Linux Privilege Escalation Awesome Script).
  • Se descarga dentro de la máquina/contenedor vulnerado.
  • Escanea versiones de Kernel, llaves expuestas, sockets libres (docker.sock), y configuraciones fatales.
  • Colorea en rojo y amarillo las vías claras de escape y hackeo nivel de administrador.

Resumen de la Taxonomía

  • El usuario cree estar a salvo (S20/S21), pero la mala configuración quiebra las APIs del Kernel.
  • El escalamiento de privilegios persigue alcanzar Ring 0.
  • Montar sockets (docker.sock) en un contenedor expuesto a la red es un pasaje sin retorno a host takeover.
  • La virtualización estricta (Hypervisores Tipo-1) aísla mejor en seguridad absoluta pero frena rendimiento. El Contenedor otorga agilidad masiva, recayendo toda la seguridad lógica en la "Auditoría de Configuración".
