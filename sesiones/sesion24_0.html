¿Qué vimos en S22 sobre criptografía?

En la Sesión 22 introdujimos amenazas y el rol del cifrado como defensa. Identificamos que:

  • Hash: función unidireccional que produce un resumen de tamaño fijo (MD5 roto, SHA-256 vigente).

Saber que el cifrado existe no es suficiente. Un profesional de sistemas debe saber cuándo y cómo aplicarlo: qué algoritmo usar, cómo gestionar las llaves y cómo verificar que la comunicación es auténtica.

Bloque conceptual A · Funciones Hash

Integridad de datos: el hash como huella digital

Una función hash criptográfica mapea datos de cualquier tamaño a un valor fijo (digest). Es determinista, unidireccional y sensible a cualquier cambio mínimo en la entrada.

Demo completa — crear archivos y verificar integridad:

# 1. Crear dos archivos de prueba $ echo "Contenido original del informe" > original.txt $ cp original.txt copia.txt # 2. Generar el hash de referencia $ sha256sum original.txt a3b4c5d6... original.txt # 3. Simular manipulación del archivo $ echo "datos extra" >> copia.txt # 4. Comparar: el hash debe diferir $ sha256sum original.txt copia.txt a3b4c5d6... original.txt f9e8d7c6... copia.txt # 5. Verificar con archivo de checksums $ sha256sum original.txt > checksums.txt $ sha256sum --check checksums.txt original.txt: OK

Propiedades de SHA-256

  • Cambiar 1 bit en la entrada produce un digest completamente distinto.
  • Es computacionalmente imposible encontrar dos entradas con el mismo hash (resistencia a colisiones).
  • No puede revertirse para obtener la entrada original.
  • Longitud fija de 256 bits, independiente del tamaño del input.

Aplica igual a ISOs de varios GB o a un archivo de texto — el digest siempre tiene 64 caracteres hex.

Bloque conceptual B · Cifrado simétrico vs asimétrico

Dos paradigmas, dos problemas distintos

Simétrico — AES

Una sola llave para cifrar y descifrar. Muy rápido, ideal para grandes volúmenes de datos.

# Crear archivo de prueba $ echo "datos confidenciales" > secreto.txt # Cifrar con AES-256 $ openssl enc -aes-256-cbc \ -pbkdf2 -in secreto.txt \ -out secreto.enc # Solicita contraseña (ej: "clave123") # Descifrar y verificar $ openssl enc -aes-256-cbc -d \ -pbkdf2 -in secreto.enc \ -out secreto_recuperado.txt $ cat secreto_recuperado.txt datos confidenciales

Asimétrico — RSA / Ed25519

Par de llaves: pública (se comparte libremente) y privada (nunca sale del dispositivo).

Solución al problema: el remitente cifra con la llave pública del destinatario. Solo la llave privada del destinatario puede descifrar.

Costo: operacionalmente más lento que AES — se usa para intercambiar claves de sesión, no para cifrar datos masivos.

En la práctica combinamos ambos: el cifrado asimétrico intercambia una clave de sesión AES de forma segura. Luego AES cifra los datos. Así funciona TLS.

Bloque conceptual C · SSH y autenticación por llave pública

SSH: el protocolo seguro del SysAdmin

SSH (Secure Shell): protocolo de red criptográfico para operar servicios de red de forma segura sobre una red insegura. Reemplaza a Telnet y rlogin que transmitían en texto plano.

La autenticación por contraseña es vulnerable a ataques de fuerza bruta. La autenticación por llave pública es resistente a estos ataques y elimina el riesgo de contraseñas débiles o robadas.

  • La llave privada nunca abandona el equipo del usuario.
  • La llave pública se copia al servidor en ~/.ssh/authorized_keys.
  • El servidor verifica que el cliente posee la llave privada mediante un desafío criptográfico.

Algoritmos recomendados (2025)

  • Ed25519: curva elíptica, llave corta (256 bits), muy rápido, preferido hoy.
  • ECDSA (P-256): compatible con más sistemas legados.
  • RSA 4096: interoperable pero más lento; evitar RSA-1024 (inseguro).

Evitar DSA (roto desde 2013) y los parámetros por defecto de RSA-2048 en contextos de alta seguridad.

Bloque conceptual C · known_hosts, TOFU y ProxyJump

Verificar la identidad del servidor: TOFU

TOFU (Trust On First Use): la primera vez que te conectas a un servidor, SSH guarda su huella pública en ~/.ssh/known_hosts. En conexiones posteriores, SSH compara la huella recibida con la guardada.

  • Si la huella cambia sin aviso, SSH alerta: posible ataque MitM o servidor reinstalado.
  • Para infraestructuras grandes, distribuir el known_hosts corporativo con Ansible o /etc/ssh/ssh_known_hosts.
# Ver el fingerprint del servidor antes de confiar $ ssh-keyscan -H servidor.com | \ ssh-keygen -lf - 256 SHA256:ABC123... servidor.com (ED25519) # Eliminar entrada obsoleta (servidor reinstalado) $ ssh-keygen -R servidor.com

SSH Jump Host / ProxyJump

Un jump host (bastión) es un servidor intermedio que sirve como único punto de entrada a una red privada. Evita exponer servidores internos directamente a Internet.

# Conectar a host interno vía bastión $ ssh -J usuario@bastion.com \ usuario@interno.local # En ~/.ssh/config (forma permanente) Host interno HostName interno.local User deploy ProxyJump usuario@bastion.com IdentityFile ~/.ssh/id_ed25519

Con ForwardAgent no en el bastión se evita que un bastión comprometido use tus llaves.

Bloque conceptual C · Cifrado de disco en reposo: LUKS

Proteger datos cuando el disco cae en manos equivocadas

El cifrado en tránsito (TLS/SSH) no protege los datos cuando el atacante tiene acceso físico al disco. LUKS (Linux Unified Key Setup) cifra particiones completas con AES-256.

# Demo sin disco físico: usar archivo loopback # 1. Instalar herramienta $ sudo apt install cryptsetup # 2. Crear imagen de 50 MB como disco virtual $ truncate -s 50M disco_demo.img # 3. Formatear como volumen LUKS2 $ sudo cryptsetup luksFormat \ --type luks2 \ --cipher aes-xts-plain64 \ --key-size 512 \ disco_demo.img # Escribe YES y elige passphrase # 4. Abrir (desbloquear) $ sudo cryptsetup open disco_demo.img datos_enc # 5. Crear fs, montar y escribir $ sudo mkfs.ext4 /dev/mapper/datos_enc $ sudo mount /dev/mapper/datos_enc /mnt/datos $ sudo sh -c 'echo "secreto" > /mnt/datos/prueba.txt' # 6. Cerrar y bloquear $ sudo umount /mnt/datos $ sudo cryptsetup close datos_enc # Sin la passphrase, disco_demo.img es ilegible

Casos de uso en producción

  • Laptops corporativas: datos ilegibles sin passphrase si el equipo es robado.
  • Backups cifrados: combinar LUKS con rsync para backups externos seguros.
  • Cumplimiento normativo: GDPR, PCI-DSS exigen cifrado de datos sensibles en reposo.

Respaldo del header: si se pierde la passphrase LUKS, los datos son irrecuperables. Siempre guardar un respaldo con cryptsetup luksHeaderBackup disco_demo.img --header-backup-file header.bak.

Bloque conceptual D · GPG y firma digital

Autenticidad e integridad de documentos

GPG (GNU Privacy Guard): implementación libre del estándar OpenPGP. Permite cifrar archivos y mensajes, y firmarlos digitalmente para garantizar su autenticidad.

Firma digital: el remitente aplica una función hash al documento y cifra ese hash con su llave privada. El receptor verifica con la llave pública. Si coincide, el documento es auténtico y no fue alterado.

  • Los paquetes de distribuciones Linux (apt, dnf) se firman con GPG.
  • Los commits de Git pueden firmarse con GPG para probar autoría.
# 1. Generar par de llaves GPG $ gpg --full-generate-key # Elegir: RSA 4096. Nombre: "Juan Test". Email: juan@test.com # 2. Crear archivo de prueba $ echo "Informe de auditoría — versión final" > reporte.txt # 3. Firmar (genera reporte.txt.asc) $ gpg --detach-sign --armor reporte.txt # 4. Verificar firma $ gpg --verify reporte.txt.asc reporte.txt gpg: Good signature from "Juan Test" # 5. Alterar el archivo y re-verificar $ echo "línea añadida" >> reporte.txt $ gpg --verify reporte.txt.asc reporte.txt gpg: BAD signature from "Juan Test" # 6. Cifrar para el mismo destinatario $ gpg --encrypt --armor \ --recipient juan@test.com reporte.txt

Bloque conceptual E · PKI: Infraestructura de Llave Pública

¿Cómo confiar en una llave pública desconocida?

El cifrado asimétrico resuelve la confidencialidad, pero introduce una pregunta crítica: ¿cómo sé que la llave pública que recibí pertenece realmente a quien dice ser y no a un atacante en el medio?

Ataque Man-in-the-Middle (MitM)

Sin verificación de identidad, un atacante puede interceptar la llave pública del servidor legítimo y sustituirla por la suya propia. El cliente cifra con la llave del atacante creyendo que es el servidor real.

La solución: Autoridades Certificadoras (CA)

Una CA es una entidad de confianza que firma digitalmente certificados X.509. El certificado vincula una llave pública con una identidad verificada (dominio, organización).

  • Root CA: anclada en el OS y navegadores.
  • Intermediate CA: emitida por la Root CA.
  • Leaf certificate: el del servidor web.

Let's Encrypt: CA gratuita y automatizada que emite certificados TLS válidos en segundos mediante el protocolo ACME. Adoptada por más del 50% de los sitios HTTPS.

PKI · Sesión 2412 / 21
Recurso visual B · Cadena de confianza PKI

La confianza se delega en cascada: el SO confía en la Root CA → la Root CA certifica a la Intermediate CA → la Intermediate CA firma el certificado del servidor. Si cualquier eslabón es inválido, el navegador muestra advertencia.

Bloque conceptual E · Inspección de certificados con openssl

Leer la información de un certificado TLS en vivo

# Demo A: inspeccionar cert de un servidor real $ openssl s_client -connect google.com:443 \ -showcerts 2>/dev/null | \ openssl x509 -text -noout | \ grep -E "Subject:|Issuer:|Not After" Subject: CN=*.google.com Issuer: C=US, O=Google Trust Services Not After: Sep 8 08:23:43 2025 GMT # Demo B: generar cert autofirmado y leerlo $ openssl req -x509 -newkey rsa:2048 \ -keyout key.pem -out cert.pem \ -days 365 -nodes \ -subj "/CN=localhost/O=PascualBravo/C=CO" # Leer el certificado generado $ openssl x509 -in cert.pem -text -noout | \ grep -E "Subject:|Issuer:|Not After|Public Key" # Ver el fingerprint SHA-256 del cert $ openssl x509 -in cert.pem \ -fingerprint -sha256 -noout

Campos clave en un certificado X.509

  • Subject: identidad que se certifica (dominio / organización).
  • Issuer: CA que firma el certificado.
  • Not Before / Not After: ventana de validez temporal.
  • Subject Alt Names (SAN): dominios adicionales cubiertos.
  • Public Key: la llave pública del servidor incluida en el cert.
  • Signature: firma digital de la CA que autentica todo lo anterior.

En cert autofirmado, Subject == Issuer — eso es lo que el navegador rechaza en producción.

La criptografía como capa transversal

S22 — Amenazas: los atacantes interceptan comunicaciones sin cifrar (sniffing), falsifican identidades (phishing/spoofing) y explotan CVEs en implementaciones criptográficas débiles (OpenSSL heartbleed, etc.).

S23 — Hardening: deshabilitar PasswordAuthentication en sshd, forzar TLS 1.2+ en servicios web, verificar firmas GPG de paquetes antes de instalar. La criptografía es el mecanismo que hace funcionar el hardening.

S24 — Criptografía aplicada: cierra el ciclo

Las herramientas (ssh-keygen, openssl, gpg) y los protocolos (TLS, SSH) son la implementación concreta de los conceptos de S22 y el mecanismo detrás del hardening de S23. Sin entender criptografía no se puede auditar si el hardening está bien hecho.
