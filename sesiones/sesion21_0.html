De la emulación de hardware a la abstracción de procesos

Recapitulación S20: El costo del Hypervisor

En la sesión anterior, vimos cómo las Máquinas Virtuales emulan por completo hardware (placa, BIOS, CPU, red).

Limitantes:

  • Arranque lento (minutos).
  • GigaBytes de peso (SO Invitado completo).
  • Asignación de RAM estática e ineficiente.

Sobrecarga (Overhead)

Correr un script de 2MB requería arrancar un Windows/Linux virtual de 20GB. ¿Es esto eficiente?

El famoso: "En mi máquina sí funciona"

Un problema recurrente en el desarrollo de sistemas operativos, scripts o aplicaciones:

  • El desarrollador compila con GCC 11.
  • El administrador de TI del servidor usa GCC 8.
  • Las dependencias, variables de entorno y versiones difieren (ej: Python 3.9 vs 3.12).
  • **Resultado:** Falla crítica al llevar a producción (o al calificar un proyecto universitario).

La Metáfora del Puerto Marítimo

Antes de 1956, los barcos cargaban café en sacos, autos sueltos, y muebles expuestos. Descargar un puerto tardaba semanas.

Solución intermodal: El Contenedor de Acero.

  • No importa qué hay dentro (café, servidores, o peluches).
  • Todos tienen dimensiones exactas.
  • Las grúas (Docker) y los barcos (Sistemas Operativos) sólo saben levantar contenedores estandarizados.

Máquina Virtual vs Contenedor

Anatomía Explicada: Menos peso, más velocidad

  • Virtualización de Hardware (VM): Virtualiza la infraestructura. Cada VM necesita su propio Kernel inútilmente replicado.
  • Virtualización de Software (Contenedor): Comparten exactamente el mismo Kernel del host.
  • Beneficio: Arrancar un contenedor tarda milisegundos (lo que tarda ejecutar un proceso común en el SO), consumiendo apenas MegaBytes de almacenamiento.

Magia Negra del Kernel Linux

Un contenedor NO es un nuevo tipo de tecnología alienígena, ni un emulador escondido. Docker "no crea" el aislamiento por arte de magia.

Un contenedor es solamente un proceso nativo del sistema que está encapsulado y mentido valiamente por el Kernel utilizando dos características geniales de Linux:

1. Namespaces

2. Cgroups

El precursor: chroot() Jails

Mucho antes de Docker (1979 - Unix V7), existía chroot (Change Root).

  • Permite decirle a un proceso que un directorio (ej. /home/usuario/carcel/) es su verdadero espacio / (Raíz temporal).
  • El proceso atrapado buscará /bin/bash pero en realidad estará leyendo /home/usuario/carcel/bin/bash.
  • Fallo de chroot: Solo encapsulaba el sistema de archivos (Filesystem). El proceso atrapado aún veía todos los procesos usando el comando ps.

1. Namespaces (Aislamiento visual lógico)

Incorporados a Linux en 2002. Son engaños estructurados que limitan lo que un proceso PUEDE VER:

  • PID: Espacios de nombres de procesos. El contenedor cree tener el PID 1, pero en el host real es el PID 14932.
  • NET: Subsistema de red. Tarjetas y puertos empaquetados. (El contenedor cree ser el único dueño del puerto 80).
  • UTS: Permite que el proceso "crea" que el sistema tiene otro Hostname paralelo.
  • MNT y USER: Aísla montajes y Mapea al usuario Root local a un usuario común en el Host real.

2. Cgroups (Control Groups)

Desarrollados por Google (2006). Mientras los Namespaces dictan qué puede ver el proceso, los Cgroups dictan cuánto puede gastar.

  • Limitan recursos estrictos físicos.
  • Restricción de CPU (ej: máximo el 15% de 1 solo Core).
  • Restricción de RAM (ej: kill-o-matic automático si supera 256MB).
  • Restringir I/O en disco.

Sin Cgroups, un contenedor infinito con fallo podría devorar el CPU del anfitrión. (Problema visto en Sesión 20).

Sistema de Archivos en Capas (UnionFS)

¿Qué pasa si 10 contenedores están corriendo la imagen de Ubuntu que pesa 70MB? ¿Ocupan 700MB de disco?

NO. Ocupan ~70MB totales en conjunto.

  • Mecanismo Copy-on-Write (CoW).
  • Todos leen la misma capa base inmutable "Ubuntu".
  • Solo si un contenedor desea escribir un archivo nuevo, se le otorga una capita fina temporal solo para él.

Inmutabilidad

Los contenedores están hechos para morir.

En el paradigma de Servidores (Pets/Mascotas): Cuidadamente mantenemos el servidor web configurándolo con amor año tras año.

En el paradigma Contenedores (Cattle/Ganado): Si algo falla, el contenedor se elimina, muere en medio segundo y se orquesta uno idéntico e impecable. El almacenamiento interno era efímero, se borra.

Docker Engine

Lanzado en 2013, Docker no inventó los contenedores, pero creó el ecosistema que lo hizo usable para programadores, uniendo Namespaces, Cgroups y UnionFS bajo comandos muy simples.

# En vez de 47 líneas de código en C para separar namespaces: $ docker run -d ubuntu

El "Docker Daemon" (dockerd) es el servicio de fondo que habla directamente con el Kernel de su sistema operativo.

Imágenes y Contenedores (Clase vs Objeto)

La Imagen (La Receta / Clase)

Archivo inerte inmutable, código preconfigurado y empaquetado (Ej. "Imagen de MySQL"). Solo ocupa espacio.

El Contenedor (El Pastel / Objeto)

Una instancia en ejecución de la Imagen. Tiene un PID, consume CPU y hace magia. Puedes lanzar N contenedores basándonos en la misma Imagen.

Construyendo la Imagen: El Dockerfile

¿Cómo creamos nuestra propia "Receta"? A través de un archivo declarativo llamado Dockerfile que automatiza la instalación del SO base y nuestras dependencias:

# 1. Definir el SO base (Imagen oficial) FROM ubuntu:22.04 # 2. Instalar dependencias dentro de la imagen RUN apt-get update && apt-get install -y python3 # 3. Copiar nuestro código al interior COPY mi_script.py /app/ # 4. Decirle al contenedor qué ejecutar al nacer CMD ["python3", "/app/mi_script.py"]

Compilarla: docker build -t mi_app_python .

Docker Hub (El registro global)

Sistemas como `apt`, `yum` o incluso `pip` dependen de un repositorio centralizado.

Docker Hub: Un registro global público. Uno solo necesita escribir un comando, y Docker buscará allí el paquete estandarizado. Contiene imágenes oficiales mantenidas por Python, Ubuntu, RedHat, etc.

Práctica 1: Hola Mundo Intercelular

Vamos a generar el proceso aislado más rápido e históricamente usado en la ingeniería.

# Levantar una terminal local. Ejecutar: $ docker run hello-world

Si el motor funciona, este comando desencadena 4 fases que analizaremos.

¿Qué ocurrió realmente? (Análisis)

  1. PULL: Como el host local no tenía hello-world, el daemon lo descargó mágicamente desde Docker Hub.
  2. CREATE: Crea un nuevo contenedor (cáscara de cgroups/namespaces) preparándolo.
  3. START: El demonio activa el contenedor. Ejecuta el código preestablecido local (Imprimir un gran hola en texto).
  4. EXIT: Como el programa terminó su trabajo de impresión, el proceso muere. Un contenedor solo vive mientras su proceso raíz esté vivo.

Práctica 2: Aislamiento Demotrado (PID namespace)

Ejecutemos un contenedor Ubuntu de modo iteractivo que se auto-destruya al salir:

$ docker run -it --rm ubuntu bash # Entrarás a un prompt root@:/# # Observa sus procesos adentro: $ su -c 'apt update && apt install procps -y && ps aux'

Resultado: Solo verá 2 procesos adentro (bash y ps). El PID 1 es "bash". Su aislamiento visual funciona implacablemente.

Práctica 3: Inspección desde el Anfitrión (Host)

No cierres la terminal del Slide anterior. Abre OTRA terminal paralela (en el host físico real).

# Desde tu equipo principal: $ ps aux | grep bash

Notarás que el proceso de "bash" del contenedor sí aparece listado en tu HOST bajo un número PID enorme (ej: 28919). El contendor le está mintiendo al proceso asilado dándole el número 1.

Ciclo de Vida y Comandos Esenciales

  • docker ps : Muestra los contenedores en ejecución.
  • docker ps -a : Muestra contenedores dormidos o muertos.
  • docker images : Listar moldes/plantillas inmutables (Pesan en disco!).
  • docker stop [ID] : Detenemos amablemente el proceso aislado principal.
  • docker rm [ID] : Desechamos el contendor para siempre.

Mito: ¿"Docker es solo para Desarrollo Web"?

Falso. Creado en GO, es una de las herramientas top para Sistemas Operativos:

  • Pruebas de scripts Bash/Kernel: Creas contenedores efímeros Alpine-Linux sin dañar el host.
  • Compilación Múltiple: Puedes compilar un binario C++ en arquitectura CentOS antigua solo ejecutando un container CentOS.
  • Networking virtual hiper-escalable. (Los vSwitches Docker manejan rutas BGP).

Sistemas Windows vs Mac vs Linux

Docker requiere el Kernel LINUX. ¿Cómo funciona en Windows o macOS de forma local?

Respuesta: WSL2 (Windows Subsystem for Linux) o HyperKit (Mac).

Actúan como mini-Hypervisors invisibles con virtualización de disco profundo, dándote un kernel falso para que dockerd opere detrás. (La hibridación definitiva entre VM y Container).

La Ilusión de la Invulnerabilidad (El Puente a S22)

El contenedor es una jaula dorada... hasta que el tigre encuentra que la reja cede.

Ya que el contendor comparte de forma real el Kernel raíz del sistema Host, si un binario comprometido tiene los privilegios adecuados y halla una vulnerabilidad 0-DAY en Linux, puede reventar el Namespace y ejecutar malware en la base real.
