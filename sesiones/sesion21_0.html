Activación de conocimiento base

El costo heredado de la Virtualización

  • En S20 vimos que una VM virtualiza hardware completo: placa, BIOS, CPU, interfaces de red.
  • Cada VM carga su propio Kernel, librerías y demonios de fondo, con gigabytes de overhead.
  • Arrancar una VM toma minutos. La RAM asignada es estática e irrecuperable.
  • El Hypervisor (software que crea y administra máquinas virtuales) introduce una capa de traducción que puede penalizar hasta un 15% del rendimiento nativo.

La gran pregunta industrial

Tiene sentido cargar un SO completo con kernel, escritorio y demonios de red solo para ejecutar un servicio MySQL de fondo que ocupa 2 MB de código?

Bloque B · Namespaces — Aislamiento visual del Kernel

Los engaños estructurados del Kernel

  • Namespaces (Linux): particionan recursos del kernel en universos aislados por proceso.
  • PID Namespace: El contenedor cree tener PID 1. En el host real puede ser PID 28919.
  • NET Namespace: Aisla interfaces y puertos; el proceso cree poseer su propia red.
  • UTS Namespace: Permite hostname propio dentro del contenedor.
  • MNT Namespace: Solo ve su propio árbol de montajes.
  • IPC Namespace: Aisla semáforos, memoria compartida y colas de mensajes.
  • USER Namespace: El root interno se mapea a un UID no privilegiado en el host.

Precursor: chroot (Unix 1979)

Encerraba un proceso en una raíz de filesystem falsa. Solo aislaba archivos; no aislaba procesos, red ni recursos del kernel.

Bloque C · Cgroups — Control de recursos

Cuánto puede gastar el proceso

  • Cgroups (Google 2006): mientras Namespaces dictan qué puede ver, Cgroups dictan cuánto puede consumir.
  • Restricción de CPU: máximo 15% de 1 core.
  • Restricción de RAM: kill automático si supera 256 MB.
  • Restricción de I/O de disco: límite de IOPS.
  • Restricción de ancho de banda de red por contenedor.

Sin Cgroups

Un contenedor con fuga de memoria podría consumir toda la RAM del host y provocar crash de servicios vecinos en el mismo servidor.

Visual C · Sistema de archivos en capas (UnionFS)

Copy-on-Write (CoW)

10 contenedores con la misma imagen Ubuntu de 70 MB no ocupan 700 MB. Comparten la capa base inmutable.

¿Qué es UnionFS?

Superpone capas de solo lectura y una capa de escritura exclusiva por contenedor. No se duplican archivos base.

Solo cuando escribe

Si el contenedor modifica un archivo, se copia solo ese archivo a su capa privada.

UnionFS · Copy-on-Write · eficiencia de almacenamiento9 / 25
Paradigma · Inmutabilidad (Cattle, not Pets)

Los contenedores están hechos para morir

  • Pets ("mascotas"): servidores tratados como únicos, con nombre propio y mantenimiento manual durante años.
  • Cattle ("ganado"): instancias intercambiables; si una falla, se reemplaza por otra idéntica desde imagen base.
  • El almacenamiento interno del contenedor es efímero.
  • La persistencia se mueve a Volumes externos.

¿De dónde salen "Pets" y "Cattle"?

Es una metáfora popularizada en prácticas DevOps y Cloud alrededor de 2012 para cambiar la operación de infraestructura: de servidores "especiales" (pets) a nodos reemplazables (cattle).

Regla práctica: en modelo pets reparas; en modelo cattle reemplazas.

Docker Engine (2013)

La unificación industrial

  • Docker no inventó contenedores; unificó Namespaces, Cgroups y UnionFS (sistema de capas con CoW visto en la diapositiva 9) bajo una interfaz simple.
  • dockerd es el daemon (proceso en segundo plano) que habla con el Kernel Linux.
  • El cliente docker CLI envía instrucciones por socket local (canal IPC local, normalmente un socket Unix en /var/run/docker.sock).
  • En lugar de decenas de syscalls manuales (llamadas directas al Kernel), un solo comando:
$ docker run -d ubuntu
docker CLI → dockerd → containerd → runc ↓ Kernel Linux (Namespaces + Cgroups)

containerd: gestiona ciclo de vida de contenedores e imágenes. runc: runtime de bajo nivel que crea el contenedor usando primitivas del Kernel.

Arquitectura Docker Engine11 / 25
Definiciones clave · Imagen vs Contenedor

Imagen (la receta)

  • Archivo inerte e inmutable.
  • Snapshot comprimido de filesystem en capas.
  • Ocupa disco; no consume CPU ni RAM.
  • Equivale a una clase en POO.

Contenedor (el objeto)

  • Instancia activa de una imagen.
  • Tiene PID real, consume CPU y RAM reales.
  • Pueden coexistir muchos desde la misma imagen.
  • Muere cuando finaliza su proceso raíz.

Dockerfile · Construcción de imagen

Archivo declarativo de build

  • Define sistema base, dependencias, código y comando de arranque.
  • Permite builds reproducibles en cualquier host con Docker.
# Dockerfile (completo para demo) FROM python:3.12-slim WORKDIR /app COPY mi_script.py /app/mi_script.py RUN useradd -m appuser && chown -R appuser:appuser /app USER appuser CMD ["python", "/app/mi_script.py"] # mi_script.py import platform print("Hola desde contenedor") print("Python:", platform.python_version()) print("SO del contenedor:", platform.system()) # Ejecución end-to-end $ docker build -t demo_s13:1.0 . $ docker run --rm demo_s13:1.0 # Compatibilidad si buildx falla $ DOCKER_BUILDKIT=0 docker build -t demo_s13:1.0 . $ docker run --rm demo_s13:1.0

Resultado esperado: imprime tres líneas (saludo, versión de Python y sistema operativo dentro del contenedor), luego termina y el contenedor se elimina por --rm. (Ver alternativas de ejecución en la siguiente diapositiva).

Dockerfile13 / 26
Alternativas de ejecución Demo s13

Opciones sin depender de build local normal

  • Opción 1: Volumen (Recomendada). Cero build local. Ejecuta usando la imagen base oficial y monta el archivo con -v. Ideal para demos rápidos y limpieza:
    $ docker run --rm -v "$PWD":/app -w /app python:3.12-slim python mi_script.py
  • Opción 2: Commit (Hack rápido). Inicia bash interactivo (-it), instala dependencias, crea archivo, sal (exit). Luego haz "commit" del estado actual:
    $ docker commit <id> demo_s13:1.0 && docker run --rm demo_s13:1.0 python /app/mi_script.py
  • Opción 3: Forzar clásico sin Buildx. Solo desactiva el nuevo motor de compilación:
    $ DOCKER_BUILDKIT=0 docker build -t demo_s13:1.0 .
  • Opción 4: Docker Hub remoto. Construir en otra máquina o CI/CD, hace push, luego localmente solo hacer docker pull nombre/demo_s13:1.0 y run.

TL;DR Demo Rápida

Para evitar fallas de buildx, la Opción 1 garantiza el resultado sin tocar la configuración local. Aísla tu código montándolo sobre una imagen inmutable garantizada.

Alternativas sin buildx14 / 26
Docker Hub · El Repositorio Global

Compartiendo nuestras imágenes

  • Docker Hub funciona igual que GitHub, pero en lugar de código fuente puro, almacena entornos completos (imágenes).
  • Cuando decimos python:3.12-slim, Docker entiende: "Descarga la imagen oficial de Python, versión 3.12, reducida (slim)".
  • Gracias a UnionFS, si descargas varias imágenes que usan la misma base (ejemplo, Ubuntu), la capa base no se duplica en tu disco.
  • El sistema compara las capas que ya tienes y solo descarga las diferencias.
# Ver las imágenes locales y su tamaño $ docker images # Descargar una imagen sin arrancar un contenedor $ docker pull ubuntu:22.04

Siempre intenta usar bases oficiales (como python o node) en lugar de instalar los lenguajes manualmente sobre distribuciones genéricas. Esto ahorra tiempo, mejora la seguridad y reduce fallas.

El clásico "Hola Mundo"

Enunciado: Ejecutar la imagen de prueba oficial de Docker y observar el comportamiento de descarga y ejecución automática.

$ docker run hello-world

¿Qué ocurre cuando presionas ENTER?

1. Docker no encuentra la imagen en tu PC. 2. La descarga (PULL) desde Docker Hub. 3. Crea un contenedor nuevo (CREATE). 4. Ejecuta el programa para saludar (START). 5. El programa termina y el contenedor "muere" (EXIT).

Este mismo flujo ocurre ya sea para imprimir un "Hola Mundo" o para encender una Base de Datos SQL completa.

Solución guiada · Entendiendo Práctica 1

La regla de oro del ciclo de vida

  1. El contenedor arranca ejecutando un único comando principal (el proceso raíz).
  2. Mientras ese proceso funciona (ej: un servidor web), el contenedor vive.
  3. En el momento que ese proceso termina, falla o se cierra, el contenedor se detiene inmediatamente.

Revisando el historial

# Ver contenedores vivos (estará vacío) $ docker ps # Ver contenedores vivos Y detenidos $ docker ps -a

hello-world solo imprime un texto y termina su trabajo al instante. Por eso, al usar docker ps inmediatamente después, no veremos nada en ejecución. El contenedor cumplió su propósito y murió.

Ciclo de vida operativo21 / 26
Errores Comunes y Troubleshooting

Respuestas directas cuando las cosas fallan

  • Fallo inmediato: Arrancas el contenedor pero nunca está en docker ps. Usa inmediatamente docker logs <ID>; allí verás un Syntax Error o archivo faltante.
  • "Port already allocated": Significa que indicaste (por ejemplo) el puerto -p 80:80, pero tu computadora física ya tiene algo (como Apache) ocupando el puerto 80 en Windows o Mac.
  • Archivo no encontrado en Volumen: Sucede cuando montas una carpeta (ej: -v ./mi_app:/app) pero estabas ubicado en el directorio equivocado en la terminal hospedadora.
  • Error de permisos con docker.sock: Tu usuario no pertenece al grupo seguro de UNIX, requieres reiniciar sesión o poner sudo (solo en Linux).

El algoritmo para reparar:

1. Usar ps -a para hallar el ID.
2. Ejecutar logs para averiguar la queja del sistema.
3. Googlear exactamente ese mensaje.

Diagnóstico común22 / 26
Docker en Windows y macOS

La capa oculta necesaria

  • Docker nace y muere dependiente del Kernel de Linux (nativos de Linux Namespaces y Linux Cgroups).
  • ¿Por qué funciona en Windows y Mac si no son Linux?
  • En Windows: Docker Desktop se encarga de instalar WSL2, que arranca inteligentemente un mini-núcleo Linux de fondo totalmente sin interfaz.
  • En Mac: Usa una VM (Máquina Virtual) altamente ligera creada por Apple.
  • El usuario sigue interactuando con docker run sin percatarse de esto, todo este puente es invisible pero vital.

El costo de la emulación

Aunque funciona de maravilla, es vital saber que el proceso tiene una milésima de demora extra compartiendo archivos a través de estas VMs en Windows y Mac, comparado contra instalar Docker de manera pura en un Ubuntu nativo de Servidor.

Síntesis Técnica Final

Diferencias absolutas que debes recordar

  • No es una Máquina Virtual en miniatura: En docker, no hay simulación de hardware ni instalación de otro núcleo entero; un contenedor es software engañado compartiendo los recursos ya existentes de forma nativa.
  • Imágenes inmutables: La plantilla oficial que descargas es como un CD-ROM grabado. No se altera internamente (UnionFS).
  • Pet vs Cattle (Avanzado): Nunca te encariñes de los contenedores. Acostúmbrate a crear, borrar y volver a crear tus proyectos en un abrir y cerrar de pestañas (Desechables). Si quieres guardar datos como una base de MongoDB, hay que adjuntar "Volúmenes".

Resumen para entrevistas de trabajo

Un contenedor te aísla con Namespaces, limita tu consumo usando CGroups, previene corromper otros entornos con UnionFS, pero comparten la misma base del SO hospedador.

La fina muralla entre Aislado e Inseguro

  • Como el contenedor comparte el Kernel activo del host principal, si alguien encuentra una vulnerabilidad directa al núcleo (0-day), vulneraría la seguridad de TODA la infraestructura.
  • Por defecto Docker es muy dócil, pero existen escenarios que son una pesadilla administrativa, como ejecutar contenedores como root.
