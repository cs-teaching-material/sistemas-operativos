Bloque conceptual A · Hardening y PoLP

¿Qué es el Hardening?

Hardening (endurecimiento) es el proceso de asegurar sistemáticamente un sistema operativo reduciendo su superficie de ataque: desactivar servicios innecesarios, reescribir políticas estrictas y eliminar configuraciones por defecto diseñadas para comodidad, no para seguridad.

Configuración por defecto

Ubuntu, Windows y Docker vienen configurados para funcionar con comodidad. El SSH acepta contraseñas. Root puede conectarse remotamente. Los contenedores arrancan con decenas de capacidades activas.

Principio de Menor Privilegio (PoLP)

Primer uso — PoLP: todo usuario, proceso o contenedor debe tener solo los privilegios estrictamente necesarios para su función, y ninguno más. Es el principio transversal que guía cada decisión de hardening.

Bloque conceptual A · Gestión de usuarios y grupos

Primera línea: controlar quién existe

  • Cuenta de servicio (-r): UID bajo (<1000), sin home, sin shell interactivo. Si el proceso es comprometido, el atacante no puede abrir sesión.
  • visudo: editor seguro de /etc/sudoers — valida la sintaxis antes de guardar. Editar el archivo directamente puede romper sudo con un typo.
  • chage (CHAnge AGE): fuerza renovación de contraseña pasado el plazo máximo.
  • passwd -l: bloquea la cuenta sin eliminarla. Útil para offboarding.
# -r = cuenta de sistema -s = shell (nologin = sin sesión) $ sudo useradd -r -s /usr/sbin/nologin nginx_svc $ sudo su - nginx_svc This account is currently not available. # Crear grupo y agregar usuario (-aG = añadir sin quitar grupos): $ sudo groupadd webadmins $ sudo usermod -aG webadmins juan $ groups juan # sudo granular — visudo valida sintaxis, nunca editar a mano: $ sudo visudo juan ALL=(ALL) NOPASSWD: /bin/systemctl restart nginx # Expiración de contraseña a 90 días: $ sudo chage -M 90 juan $ sudo chage -l juan # verificar # Bloquear cuenta (LK=locked, PS=activa): $ sudo passwd -l nombre_usuario $ sudo passwd -S nombre_usuario

Bloque conceptual B · Hardening de OpenSSH

SSH es la puerta de entrada — endurecerlo es prioridad

Ed25519 es un algoritmo de clave pública basado en curvas elípticas. Es más corto, más rápido y más seguro que RSA-2048. Una clave privada Ed25519 no puede ser forzada con los recursos computacionales actuales.

Orden crítico: primero copiar la clave pública al servidor, luego deshabilitar autenticación por contraseña. Invertir el orden bloquea el acceso permanentemente.

CIS Benchmark 5.2.8: PermitRootLogin no es requisito mínimo en cualquier auditoría de seguridad industrial.

# PASO 1 — Generar clave Ed25519 (en la máquina cliente): $ ssh-keygen -t ed25519 -C "juan@empresa" -f ~/.ssh/id_ed25519 # Crea dos archivos: # id_ed25519 → clave PRIVADA (nunca sale de tu máquina) # id_ed25519.pub → clave PÚBLICA (se copia al servidor) # PASO 2 — Copiar clave pública al servidor: $ ssh-copy-id -i ~/.ssh/id_ed25519.pub juan@servidor # Agrega la clave a ~/.ssh/authorized_keys en el servidor # PASO 3 — Verificar login con clave ANTES de cambiar config: $ ssh -i ~/.ssh/id_ed25519 juan@servidor # PASO 4 — Editar /etc/ssh/sshd_config en el servidor: PermitRootLogin no # root no puede conectarse por SSH PasswordAuthentication no # solo claves, nunca contraseñas PubkeyAuthentication yes Port 2222 # cambiar puerto reduce bots automáticos AllowUsers juan maria deploy_bot # PASO 5 — sshd -t valida la sintaxis sin reiniciar # (un error en sshd_config con el servicio ya reiniciado = acceso perdido) $ sudo sshd -t $ sudo systemctl restart sshd $ ss -tlnp | grep sshd # confirmar que escucha en puerto 2222

Bloque conceptual B · Integridad del sistema con AIDE

Detectar modificaciones de archivos del sistema

Un rootkit es malware que modifica binarios del sistema (/usr/bin/ps, /usr/bin/ls) para ocultarse — el propio sistema miente sobre lo que está corriendo.

AIDE (Advanced Intrusion Detection Environment) calcula un hash criptográfico (huella digital única) de cada archivo del sistema. Si el contenido de un binario cambia aunque sea un byte, su hash cambia. AIDE detecta esa diferencia comparando contra la base registrada antes del ataque.

  • La base de hashes se genera en un sistema limpio (línea base).
  • Debe guardarse en un medio externo confiable — si el rootkit también controla AIDE, puede falsificar la comparación.
# PASO 1 — Instalar AIDE: $ sudo apt install aide aide-common # PASO 2 — Generar base de datos inicial (tarda ~2 min): $ sudo aideinit # Crea /var/lib/aide/aide.db.new con hashes de todo el sistema # PASO 3 — Activar la base (obligatorio, si no --check falla): $ sudo cp /var/lib/aide/aide.db.new /var/lib/aide/aide.db # PASO 4 — Simular una modificación maliciosa: $ sudo touch /usr/bin/aide_test_tamper # PASO 5 — Detectar el cambio: $ sudo aide --check AIDE found differences between database and filesystem! Added entries: /usr/bin/aide_test_tamper # Limpiar y actualizar la base tras cambios legítimos: $ sudo rm /usr/bin/aide_test_tamper $ sudo aide --update $ sudo cp /var/lib/aide/aide.db.new /var/lib/aide/aide.db

Bloque conceptual C · Linux Security Modules

AppArmor y SELinux: vigilantes del Kernel

Linux Security Modules (LSM) interceptan toda llamada al sistema antes de que toque el hardware, evaluándola contra un perfil predefinido. Incluso si el proceso tiene uid=0 (root), el kernel puede denegar la operación.

AppArmor

Adoptado por Ubuntu/Debian. Asigna perfiles de comportamiento por ruta del ejecutable. Más legible que SELinux. Docker en Ubuntu inyecta automáticamente un perfil AppArmor a cada contenedor creado.

Dos modos: enforce (bloquea la operación y la registra) vs complain (solo registra, no bloquea — útil para crear perfiles nuevos sin romper el sistema).

# Ver perfiles activos y su modo: $ sudo aa-status # Cambiar un perfil a modo complain (para pruebas): $ sudo aa-complain /usr/sbin/nginx # Volver a enforce (producción): $ sudo aa-enforce /usr/sbin/nginx

SELinux

Creado originalmente por la NSA. Estándar en RHEL/CentOS/Fedora. Control de acceso obligatorio (MAC): incluso root no puede hacer lo que la política prohíbe. Sintaxis compleja pero extremadamente potente.

MAC (Mandatory Access Control): el kernel impone políticas que no pueden ser sobrescritas por ningún usuario, ni siquiera root. Contrasta con DAC (Discretionary), donde el dueño del archivo decide los permisos.

Bloque conceptual C · SecComp — filtrado de syscalls

Amputar las syscalls que la app no necesita

SecComp (Secure Computing Mode) restringe las llamadas al sistema disponibles para un proceso. Un Kernel moderno expone ~350 syscalls; una app promedio usa ~50. SecComp permite bloquear las 300 restantes.

Si el proceso invoca una syscall vetada, el kernel lo mata con SIGKILL — la señal de terminación inmediata que no puede ser ignorada ni capturada por el proceso.

El perfil se define en JSON con dos acciones posibles: SCMP_ACT_ALLOW (permitir la syscall) y SCMP_ACT_ERRNO (rechazarla y devolver un error al proceso, sin matarlo — útil para pruebas).

Bloque conceptual D · Linux Capabilities

Dividir el poder de root en piezas

Linux Capabilities descomponen el poder total de root (uid=0) en ~40 capacidades independientes. Cada proceso puede tener solo las que necesita.

CapabilityPermite
CAP_NET_BIND_SERVICEAbrir puertos <1024 sin ser root
CAP_SYS_TIMEModificar el reloj del sistema
CAP_SYS_MODULECargar/descargar módulos del kernel
CAP_SYS_ADMINOperaciones administrativas generales — casi equivale a root total

Docker y capabilities

Docker elimina por defecto CAP_SYS_TIME y CAP_SYS_MODULE de todos los contenedores. Muchos exploits de Zero-Day dependen exactamente de estas capabilities para operar.

Bloque conceptual D · Hardening de contenedores

Contenedores con privilegios mínimos

cap-drop=ALL + cap-add selectivo

Desactiva todas las capabilities y luego agrega solo la estrictamente necesaria. Si un atacante compromete el contenedor, no puede invocar ninguna operación privilegiada que no estuviese explícitamente habilitada.

$ docker run -d \ --cap-drop=ALL \ --cap-add=NET_BIND_SERVICE \ nginx # NET_BIND_SERVICE: único privilegio que nginx necesita # (abrir puerto 80, que es < 1024)

--read-only + --tmpfs

Hace el sistema de archivos del contenedor inmutable. El malware no puede descargar herramientas ni modificar librerías. --tmpfs monta un sistema de archivos temporal en memoria solo para las rutas que realmente necesitan escritura — desaparece al detener el contenedor.

$ docker run -d \ --read-only \ --tmpfs /tmp \ --tmpfs /var/cache/nginx \ nginx # /tmp y el cache: escribibles en RAM, solo mientras corre # El resto del sistema de archivos: inmutable

Recurso visual B · Hardening en el Dockerfile

Dockerfile inseguro

FROM ubuntu:latest # La app corre como root (uid=0) COPY mi_app /app/mi_app CMD ["/app/mi_app"] # Si mi_app es comprometida, # el atacante tiene root inmediato.

Dockerfile endurecido

FROM ubuntu:22.04 # Crear usuario sin privilegios: RUN useradd -ms /bin/bash appuser COPY mi_app /app/mi_app RUN chown appuser:appuser /app/mi_app # Cambiar a usuario no-root: USER appuser CMD ["/app/mi_app"] # Si comprometida: uid=1001, sin shell útil.

La directiva USER en el Dockerfile previene la escalada del 90% del malware inyectado vía vulnerabilidad web.

Bloque conceptual E · Contenedores rootless

¿Qué pasa si el daemon Docker es comprometido?

dockerd normalmente corre como root. Si hay una vulnerabilidad en el daemon, el atacante obtiene root en el host directamente — sin necesitar un Container Breakout.

Rootless Mode: el daemon dockerd y todos sus contenedores corren bajo un usuario ordinario sin privilegios. Si ocurre un breakout, el atacante aterriza en el host como ese usuario, sin capacidad de escalar.

Podman es una alternativa a Docker que es rootless por diseño — no tiene daemon central corriendo como root. Cada contenedor es un proceso hijo directo del usuario que lo lanzó.

Activar Docker Rootless

# Prerrequisito: instalar uidmap (mapeo de UIDs en namespaces): $ sudo apt install uidmap # Instalar el modo rootless para el usuario actual: $ dockerd-rootless-setuptool.sh install # Iniciar el daemon bajo el usuario actual (no root): $ systemctl --user start docker $ systemctl --user enable docker # arrancar en cada login # Verificar: dockerd ya no corre como root $ ps aux | grep dockerd juan 1234 dockerd ... # uid=1000, no root # Configurar la variable de entorno para este usuario: $ export DOCKER_HOST=unix://$XDG_RUNTIME_DIR/docker.sock

Práctica en clase 2 · SecComp personalizado

Bloquear una syscall específica con un perfil JSON

Enunciado: crear un perfil SecComp que bloquee la syscall mkdir y verificar que el contenedor no puede crear directorios. El perfil usa SCMP_ACT_ERRNO (devuelve error al proceso) en lugar de SCMP_ACT_KILL (mataría el proceso), lo que permite observar el rechazo sin que el contenedor termine.

PASO 1 — Crear el archivo del perfil en el host:

# En la máquina host (no dentro del contenedor): $ mkdir -p ~/seccomp-demo $ cat > ~/seccomp-demo/deny-mkdir.json <<'EOF' { "defaultAction": "SCMP_ACT_ALLOW", "syscalls": [{ "names": ["mkdir", "mkdirat"], "action": "SCMP_ACT_ERRNO" }] } EOF # defaultAction ALLOW = todo permitido por defecto # Solo mkdir y mkdirat quedan bloqueadas $ cat ~/seccomp-demo/deny-mkdir.json # verificar

PASO 2 — Lanzar y probar:

# --security-opt seccomp= aplica el perfil al contenedor # La ruta debe ser absoluta (no relativa): $ docker run --rm -it \ --security-opt \ seccomp=$HOME/seccomp-demo/deny-mkdir.json \ alpine sh # Intentar crear directorio — debe fallar: / # mkdir prueba mkdir: can't create directory 'prueba': Operation not permitted # Verificar que otras operaciones funcionan normalmente: / # touch archivo.txt # debe funcionar (usa syscall open/creat) / # ls # debe funcionar

El kernel interceptó mkdir, la cruzó con el perfil y la rechazó. El resto del contenedor sigue funcionando normalmente.

Bloque conceptual F · Hardening de red

Limitar conectividad saliente del contenedor

Después de comprometer un contenedor, el atacante necesita conectarse a su servidor de Command & Control (C2) para recibir instrucciones y exfiltrar datos.

Si la base de datos solo sirve consultas internas, ¿por qué tiene permitido hacer ping 8.8.8.8 o abrir conexiones salientes al exterior?

# PASO 1 — Crear red interna aislada (sin acceso a internet): $ docker network create \ --internal \ --driver bridge \ red_interna # PASO 2 — Lanzar la base de datos en esa red (con nombre): $ docker run -d \ --name postgres_db \ --network red_interna \ -e POSTGRES_PASSWORD=secreto \ postgres:16 # PASO 3 — Verificar que el contenedor no puede alcanzar internet: $ docker exec postgres_db ping -c2 8.8.8.8 ping: connect: Network is unreachable # PASO 4 — Verificar que otro contenedor en la misma red sí puede comunicarse: $ docker run --rm --network red_interna alpine \ ping -c2 postgres_db # debe responder # Limpiar: $ docker stop postgres_db && docker rm postgres_db $ docker network rm red_interna

Bloque conceptual F · Ciclo de vida y parches

Hardening no es un evento — es higiene rutinaria

Una política SecComp y AppArmor perfectas no protegen contra un CVE publicado ayer en el Kernel que todavía no fue parcheado.

  • Dirty COW (CVE-2016-5195) y Dirty Pipe (CVE-2022-0847): dos vulnerabilidades del kernel de Linux que permitían a cualquier proceso sin privilegios sobrescribir archivos de solo lectura — incluyendo /etc/passwd. Un atacante dentro de un contenedor podía usarlas para escalar a root en el host, saltando AppArmor y SecComp porque el exploit operaba dentro del propio kernel.
  • El dilema del uptime: un servidor que lleva meses sin reiniciarse probablemente tiene un kernel con CVEs críticos sin aplicar en memoria.

Reiniciar es obligatorio

apt upgrade descarga e instala el nuevo kernel en disco, pero el kernel viejo sigue corriendo en memoria hasta el próximo reinicio. Ubuntu crea el archivo /var/run/reboot-required automáticamente cuando hay un parche que requiere reinicio.

# Ver el kernel corriendo ahora mismo: $ uname -r 6.8.0-51-generic # Ver kernels instalados en disco (puede haber uno más nuevo): $ dpkg -l 'linux-image-*' | grep '^ii' | awk '{print $2}' # Ubuntu indica automáticamente si hay reinicio pendiente: $ [ -f /var/run/reboot-required ] && \ cat /var/run/reboot-required.pkgs # Si muestra linux-image-X.X.X = hay kernel nuevo sin activar # Aplicar parches y reiniciar en ventana de mantenimiento: $ sudo apt update && sudo apt upgrade -y $ sudo reboot

Síntesis técnica

Resumen de operaciones defensivas

Usuarios y grupos: cuentas de servicio sin shell (nologin), sudo granular con visudo, contraseñas con expiración (chage -M 90).

Criptografía operativa: SSH solo con claves Ed25519, PasswordAuthentication no. AIDE para monitoreo de integridad de binarios del sistema.

Kernel LSM: AppArmor en modo enforce en Ubuntu. SecComp para filtrar syscalls no usadas por la app. Ningún perfil es mágico — debe ser específico para la app.

Contenedores: --cap-drop=ALL + solo capabilities necesarias. --read-only con tmpfs para lo escribible. Directiva USER en el Dockerfile. Nunca --privileged en producción.

El problema del hardening manual

Aplicar --cap-drop=ALL y --read-only a mano en cada docker run es lento y propenso al olvido humano. Una infraestructura con cientos de contenedores hace esto imposible de mantener de forma consistente.

¿Y si el hardening pudiera estar codificado, versionado en Git y aplicado automáticamente por un robot cada vez que se despliega?
