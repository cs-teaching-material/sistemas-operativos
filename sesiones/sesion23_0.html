Transformando vulnerabilidades en fortalezas de infraestructura

Recapitulación S22: La Jaula Rota

En la Sesión 22 vimos que una mala configuración (ej: `--privileged` o montar `/var/run/docker.sock`) permite a un atacante con acceso a un contenedor escalar a Ring 0.

El Kernel subyacente es compartido; la debilidad de un proceso aislado compromete al hardware físico real.

El Reto Defensivo

Cerrar explícitamente cada vector de ataque inyectando restricciones matemáticas ineludibles al Kernel y a las aplicaciones.

¿Qué es el Hardening?

Proceso de aseguramiento sistemático de un sistema operativo, reduciendo drásticamente su superficie de ataque (Attack Surface).

  • Por defecto: Los sistemas (como Ubuntu, Windows, Docker) vienen configurados para funcionar con comodidad, no con seguridad absoluta.
  • Hardening: Desactiva servicios innecesarios, reescribe políticas estrictas y elimina la "comodidad" a favor de la supervivencia.

Principio de Menor Privilegio (PoLP)

Un usuario, programa o proceso solo debe tener los privilegios estrictamente necesarios para realizar su tarea legítima. Ni más, ni menos.

Ejemplo clásico:

  • Un servidor web (Nginx) solo necesita leer archivos HTML y transmitirlos por el puerto 80 o 443.
  • No necesita privilegios para modificar contraseñas (`/etc/shadow`) ni para formatear discos duros (`fdisk`). Si lo tiene, viola el PoLP.

Defensa en Profundidad (El modelo "Cebolla")

El Estándar de la Industria: CIS Benchmarks

Center for Internet Security (CIS) define reglas de hardening comprobadas universalmente. Si trabajas operando sistemas operativos, los leerás a diario.

Ejemplos de directivas CIS para Linux:

  • 1.1.1.1 - Deshabilitar el montaje del sistema de archivos cramfs (Inseguro).
  • 5.2.1 - Asegurar que los permisos en `/etc/ssh/sshd_config` sean 600.
  • 5.2.8 - Deshabilitar acceso root directo por SSH (PermitRootLogin no).

Kernel Security Modules (LSM)

El estándar NameSpaces/Cgroups aísla... pero no juzga la intención del programa (si un programa aislado hace cosas legales, se le permite).

Los Linux Security Modules (LSM) actúan como un vigilante paranoico interceptando TODA llamada antes de que toque el hardware real, evaluándola con un perfil predefinido.

Dos titanes reinan hoy: SELinux y AppArmor.

SELinux (Control de Acceso Obligatorio - MAC)

Creado originalmente por la NSA (Agencia de Seguridad Nacional de EE.UU). Viene embebido típicamente en distribuciones derivadas de RedHat (RHEL, CentOS, Fedora).

  • Incluso si el atacante consigue acceso `root`, si una política SELinux dice explícitamente "El servidor web Apache NO puede ejecutar comandos en la terminal externa", el Kernel denegará la petición a nivel Ring 0.
  • Fama: Increíblemente poderoso, pero la sintaxis de sus perfiles es famosa por ser desesperantemente compleja.

AppArmor (Application Armor)

La alternativa adoptada por distribuciones Debian/Ubuntu y Suse. Más legible y fácil de gestionar que SELinux.

  • Asigna "Perfiles de comportamiento" por ruta de programa.
  • Docker en Ubuntu instala e inyecta un perfil genérico de AppArmor por defecto a cada contenedor que creas. (Por eso evitamos escapes inmediatos).
  • Modo Enforce (bloquea) vs Complain (solo registra la alerta pero permite).

Seccomp (Secure Computing Mode)

Una característica independiente dentro del Kernel enfocada solo en restricciones de llamadas al sistema (Syscalls).

  • Un Kernel Linux moderno tiene cerca de ~350 syscalls distintas (reboot, mount, chown, mkdir, chroot...).
  • Una aplicación promedio usa apenas 40 o 50 syscalls distintas en toda su vida.
  • Seccomp permite filtrar o amputar las 300 syscalls restantes. Si el proceso invoca un comando vetado, el kernel asesina al proceso inmediatamente con un `SIGKILL`.

Arquitectura Syscall bajo Seccomp

Contenedor "Confiable"

Proceso Nginx intenta read() un HTML.

-> Perfil Seccomp: ¿Está read permitido en la whitelist? ¡Sí!

-> Kernel permite leer el disco.

Contenedor Vulnerado

Nginx infectado intenta reboot() al sistema base.

-> Perfil Seccomp: ¿Está reboot en la whitelist? ¡No!

-> Kernel asesina implacablemente a Nginx. El OS Base se salva.

Práctica 1: Evaluando Capacidades Base

Linux usa un concepto llamado "Capabilities" para dividir el poder total de Root en pedacitos (ej: `CAP_CHOWN`, `CAP_NET_ADMIN`).

Observaremos mediante comando qué "Poderes de root" reales le da Docker a un contenedor estándar por defecto usando `capsh`:

# Desde tu terminal host corre un test aislado interactivo: $ docker run --rm -it alpine sh # Ya adentro del contenedor, instalar libreria util y revisar privilegios / # apk add libcap / # capsh --print

Análisis de la Práctica (Qué retira Docker)

El resultado del comando capsh --print evidenciará algo inaudito: Incluso operando como "root" dentro del contenedor, el Kernel te ha revocado la capacidad cap_sys_time y cap_sys_module.

  • No puedes cambiarle la hora al reloj del anfitrión físico.
  • No puedes instalar drivers exóticos al hardware de red (Kernel modules).
  • Mitigación instantánea: Muchos Zero-Days dependen del uso de estos poderes para invadir a nivel módulo.

Hardening Docker: Drop All Capabilities

Si sabemos que nuestro script web solo procesa texto... ¿Para qué tener siquiera los poderes de red (`CAP_NET_RAW`)? Apliquemos PoLP absoluto:

# Arrancando con 0 poderes mágicos, despojando TODOS los remanentes: $ docker run -d --cap-drop=ALL nginx

Este contenedor será prácticamente inútil para cualquier atacante. Aunque logre ingresar bajo modo consola, toda invocación al anillo cero explotará (Ej: inhabilitado de efectuar el más mínimo `chown`).

Contenedores Rootless (Sin dockerd root)

El daemon de Docker (`dockerd`) requiere usualmente ejecutarse como administrador en Linux. Si crashea dockerd, el host cae.

Solución moderna: Rootless Mode o Podman.

Ejecutar los contenedores y al propio motor detrás de un subsistema atado al usuario regular. Incluso si ocurre un Breakout (Escape - S22), el hacker aterrizará en el SO anfitrión como usuario "pepito" de clase baja, sin poder quebrar el Ring 0.

Sistemas de Archivos Inmutables (Read-Only Root)

¿Por qué permitir a un atacante que descargue sus herramientas (`wget exploit.sh`) o modifique librerías infectadas (`/lib/...`) en el entorno de ejecución?

# Hardening de inmutabilidad (Solo lectura): $ docker run -d --read-only nginx

Todo el disco virtual se vuelve una roca. Solo se admiten escrituras en carpetas exentas temporales configuradas manualmente (Ej: `/tmp`). El malware moderno no puede anclarse ni sobrevivir a esto.

Hardening por Red (Network Limits)

Si logran vulnerar tu interfaz, la fase 2 del atacante es conectarse de vuelta a su servidor para descargar instrucciones (Command and Control - C2).

  • Si el contenedor ejecuta solo una Base de Datos local... ¿Por qué tiene permitido hacer ping 8.8.8.8 o abrir túneles salientes al exterior por HTTP?
  • Regla Defensiva: Aislar siempre mediante iptables, UFW, o redes puente Docker aisladas prohibiendo tráfico de salida (Outbound) ciego.

Práctica 2: El comando prohibido (Seccomp Personalizado)

En lugar de delegar en el perfil estándar, podemos proveer un JSON donde bloqueamos las llamadas a crear nuevas carpetas (`mkdir`).

# Imagina tener profile.json bloqueando mkdir. Al llamarlo: $ docker run --security-opt seccomp=profile.json -it alpine sh / # mkdir carpeta_hack mkdir: can't create directory 'carpeta_hack': Operation not permitted

Conclusión: El código intenta ordenar a Ring 0 crear un directorio en Disco. El Ring 0 lo intercepta, cruza con la política JSON, y amputa el proceso. (Syscall capada).

Automatizando el Escaneo en Construcción

Hardening no es solo "apagar cosas". Es auditar *antes* de desplegar.

Escáner de Imágenes (Trivy, Clair): Herramientas que analizan tu plantilla contenedorizada offline en búsqueda de vulnerabilidades conocidas (CVE) obsoletas incrustadas, evaluando si las librerías `openssl` instaladas están marchitas y requieren actualización programada urgente.

Hardening en el Dockerfile (La fase del Desarrollador)

El error más grande proviene de la imagen madre generada de mal modo (Sesión 21/22).

FROM ubuntu:latest # ERROR 1: Ejecutar la app compilada siendo ROOT. COPY mi_app /app # SOLUCIÓN: Crear un usuario común sin permisos e instruir su uso: RUN useradd -ms /bin/bash usuario_debil USER usuario_debil CMD ["./app"]

La simple orden `USER` previene la escalada del 90% del malware inyectado vía web.

Manejo de Parches y Ciclo de Vida Lifecycle

El Hardening no es una pastilla mágica que se toma una vez y dejas al sistema tirado. Requiere higiene rutinaria.

Patch Management: Si tu política SELinux y Seccomp son geniales, pero no actualizaste el Kernel base en 4 años de producción (Uptime absurdo), un atacante descubrirá un CVE que permite atravesar mágicamente esas paredes (Dirty Pipe / Dirty COW).

Reiniciar es vital: Un Kernel solo se actualiza cuando el sistema operativo arranca la tabla de memoria física en el nuevo módulo base.

Resumen de Operaciones Defensivas

  • No delegues todo a contenedores: Modifica y endurece tu OS base instalando AppArmor y deshabilitando módulos USB no usados o redes obsoletas (IPX).
  • Inactiva el uso de permisos SUID sobre comandos ajenos.
  • Implementa bloqueos draconianos reduciendo al usuario solo a perfiles PoLP.
  • Al levantar contenedores, suma banderas defensivas: `--cap-drop=ALL` y `--read-only`. Obliga al atacante a pelear inútilmente por privilegios contra la muralla.

La Transición Inminente al CI/CD

Realizar hardening a mano servidor por servidor, contenedor por contenedor es lento y sumamente propenso a falencias humanas (alguien olvida usar el comando DropCap).

¿Qué sigue? Estandarizar la seguridad en configuraciones automatizadas persistentes.
